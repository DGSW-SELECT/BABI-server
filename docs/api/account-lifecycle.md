# 로그아웃과 회원탈퇴

- `POST /auth/logout`: 본문 없이 호출한다. 유효한 액세스 토큰이 있으면 남은 유효기간 동안 폐기하며 연결된 세션도 삭제한다. 액세스 토큰이 만료되거나 없더라도 리프레시 쿠키의 비밀값이 일치하면 해당 세션을 삭제한다. 쿠키 인증 요청에는 `X-CSRF-Token` 헤더가 필요하다. 쿠키 삭제 응답은 Redis 장애 시에도 내려가지만 서버 측 세션 폐기 보장은 불가능하며 503을 반환한다.
- `POST /auth/refresh`: 리프레시 쿠키와 CSRF 헤더로 단일 사용 리프레시 토큰을 원자적으로 교체한다. 기존 로그인 응답의 `accessToken`도 유지한다.
- `DELETE /auth/account`: 인증 후 `{"password":"현재 비밀번호"}`를 전달한다. 계정을 익명화하고 보호자 행을 소프트 삭제하며 권한과 대기 중 초대를 정리한다. 다른 보호자가 있는 아기의 유일한 OWNER는 먼저 권한을 이전해야 한다(409 `ACCOUNT_OWNER_TRANSFER_REQUIRED`).

인증된 요청은 Redis 세션과 사용자 DB 상태를 확인한다. `sid`가 없는 이전 액세스 토큰은 기존 클라이언트 호환을 위해 만료 시까지 폐기 목록과 계정 상태를 확인하며, 기존 토큰의 최대 수명과 클라이언트 전환이 확인된 뒤 지원 제거를 검토해야 한다. 즉시 탈퇴·로그아웃을 반영하기 위해 사용자 상태 캐시를 두지 않는다. Redis 장애 또는 데이터 유실에 대비한 보존 및 복구 정책이 필요하다.

쿠키는 host-only, HttpOnly(인증 쿠키), Secure 및 SameSite=Lax로 설정한다. 운영에서는 HTTPS와 신뢰할 수 있는 같은 사이트 도메인, 엄격한 CORS 허용 목록, 신뢰하지 않는 하위 도메인으로부터 쿠키 주입을 막는 배포 구성이 필요하다. 현재 CSRF는 서명되지 않은 double-submit 방식으로, 하위 도메인 쿠키 주입을 완전히 방어하지 못한다. 로그인은 JSON 요청과 CORS 검증에 의존하므로 허용 출처를 엄격하게 관리해야 하며, 세션에 바인딩된 CSRF와 로그인 CSRF 강화는 후속 보안 검토가 필요하다. 서로 다른 site의 프론트엔드라면 현재 SameSite=Lax 설정으로 쿠키가 전송되지 않을 수 있다.
