# 아기 정보 부분 수정과 삭제 정책 검토

2026-10-28 KST, `feature/baby-registration` 기준.

## 구현한 수정 API

`PATCH /babies/{babyId}`. 기존 JWT Bearer 인증이 필요하며 사용자 ID는 JWT principal에서 가져온다. 해당 아기의 현재 OWNER만 수정할 수 있다.

```json
{"name":"새 이름"}
```

```json
{"birthDate":"2025-03-01"}
```

- 두 필드를 함께 전달할 수도 있다. 생략한 필드는 기존 값을 유지한다.
- `{}`는 OWNER 권한을 확인하고 현재 정보를 반환하는 무변경 요청이다.
- 명시적인 `null`은 허용하지 않는다. 필드 생략과 구분하며 400 `INVALID_REQUEST_BODY`로 응답한다.
- 이름은 빈 문자열·공백만 있는 값·50자 초과를 거부한다. 출생일은 ISO 날짜이며 미래 날짜를 거부한다.
- Bean Validation 실패는 400 `VALIDATION_ERROR`, 파싱 실패·타입 오류·잘못된 JSON은 400 `INVALID_REQUEST_BODY`다.
- 성공은 200이며 기존 `ApiResponse<BabyReadResponse>`를 사용한다.

```json
{
  "success": true,
  "message": "아기 정보 수정에 성공했습니다.",
  "data": {
    "babyId": 123,
    "name": "새 이름",
    "birthDate": "2025-03-01"
  }
}
```

유효한 요청 기준으로 아기 없음은 404 `NOT_FOUND`, MEMBER·비보호자는 403 `FORBIDDEN`, 미인증은 401 `UNAUTHORIZED`, 잘못된 JWT는 401 `INVALID_TOKEN`이다. 입력 검증은 기존 MVC 처리 순서를 따른다.

기존 `findByIdForUpdate`로 아기 행을 잠근 뒤 OWNER를 검사한다. 권한 위임·탈퇴와 같은 잠금 기준을 사용하므로 위임이 커밋된 후에는 이전 OWNER의 수정 요청을 거부한다. 기존 등록·조회·목록·보호자 API 구현은 변경하지 않았다.

## 삭제 분석: 구현 보류

요청에 명시된 “정책 미확정 또는 다른 도메인 영향이 있으면 삭제 로직을 임의 구현하지 않는다”는 조건에 따라 `DELETE /babies/{babyId}`는 추가하지 않았다. 성공을 가장하는 임시 API도 없다.

### 확인한 코드와 실제 로컬 DB

| 확인 대상 | 결과 |
|---|---|
| `Baby` | `babies` 매핑. 논리 삭제 필드 없음. `createdByUserId`는 단순 ID이며 User와 JPA 관계 없음 |
| `BabyMember` | `baby_members` 매핑. `babyId`, `userId`는 단순 ID. `(baby_id, user_id)` UNIQUE 존재 |
| JPA 연관 관계 | 아기 관련 `@ManyToOne`, `@OneToMany`, cascade, orphanRemoval 없음 |
| 현재 저장소의 다른 엔티티 | User만 존재. 육아 기록·AI 리포트 엔티티/삭제 정책 없음 |
| 실제 로컬 MySQL | `compose.yml`과 일치하는 `babi-server-mysql-1` 컨테이너의 `babi` 스키마를 읽기 전용 조회 |
| 로컬 테이블 | `babies`, `baby_members`, `users` |
| 실제 로컬 외래 키 | `information_schema.KEY_COLUMN_USAGE`의 참조 외래 키 조회 결과 0건 |
| 현재 공유/배포 DB | 접속하지 않음. 로컬 결과를 다른 환경의 스키마 보장으로 사용할 수 없음 |
| 기존 SQL 백업 | 2026-10-25 users 테이블만 포함. 최신 전체 스키마 근거로 사용할 수 없음 |

DB 확인에는 테이블·열·외래 키 메타데이터 SELECT만 사용했다. 서비스 실행, 데이터 조회·변경, DDL·마이그레이션은 수행하지 않았다. 외래 키가 없다는 사실은 다른 서비스나 코드에서 참조하지 않는다는 보장이 아니다.

### 예상 영향과 대안

| 방식 | 영향 | 호환성 및 필요한 결정 |
|---|---|---|
| 물리 삭제 | `baby_members` 관계와 `babies` 행을 하나의 트랜잭션에서 정리해야 함. users는 삭제 대상 아님 | 외래 키 자동 cascade 없음. 기록·리포트의 외부 참조와 보존 정책을 먼저 확정해야 함. 커밋 후 상세는 404, 목록에서는 제외되는 계약 필요 |
| 논리 삭제 | 삭제 시각/상태로 아기와 기록을 보존할 수 있음 | 스키마 변경 및 기존 상세·목록·보호자 조회·권한 변경 경로의 삭제 상태 검사 필요. 표시만 숨기면 기존 API로 계속 접근할 수 있음 |

다른 도메인의 기록을 보존하거나 복구할 가능성이 있다면 논리 삭제를 우선 권고한다. 다만 이번 작업의 기존 기능 유지 범위를 넘어 스키마와 모든 접근 경로를 조정해야 하므로 지금 일부만 적용하지 않았다. 모든 도메인의 영구 삭제가 승인되고 참조 처리가 정리된 경우에는 물리 삭제를 선택할 수 있다.

다음 정책을 먼저 결정해야 한다.

1. 삭제는 영구 파기인가, 보관/복구 가능한 숨김인가?
2. 육아 기록·AI 리포트·초대 등 다른 도메인의 참조와 보존 책임은 무엇인가?
3. 논리 삭제라면 BabyMember 관계 보존·복구 방식과 재초대 가능 여부는 무엇인가?
4. 삭제 이후 상세·목록·보호자 관리·반복 삭제의 상태 코드는 무엇인가?
5. 실제 대상 환경의 최신 외래 키와 다른 서비스 참조가 모두 확인됐는가?

정책 확정 후 OWNER 성공, MEMBER/비보호자 거부, 미인증, 없는 아기, 삭제 후 상세·목록·관계 정리, 실패 시 롤백 및 동시 위임과의 경합 테스트를 구현해야 한다. 이번에는 삭제 테스트를 통과했다고 보고하지 않는다.

## 검증

- `./gradlew compileJava`: 성공.
- 임시 Gradle init script와 환경 설정으로 실제 Redis가 필요한 `EmailSignupIntegrationTest`를 제외하고 메모리 H2 테스트 실행.
- 테스트 프로필과 H2 JDBC URL을 고정하고 Redis/SMTP 대상은 로컬 비서비스 포트로 고정. 테스트 DB 접속 로그도 `jdbc:h2:mem:`으로 확인.
- 총 271건 통과, 실패/오류/건너뜀 0. 실행 대상에서 제외한 실제 Redis 통합 테스트는 이 수치에 포함하지 않는다.
- 기존 245건에 수정·입력 경계·미인증·권한·404·권한 위임 경합·OpenAPI 계약 검증 26건 추가.
- Swagger 생성 결과에서 PATCH의 선택적 name/birthDate와 기존 응답 구조를 검증. 미구현 DELETE가 문서에 노출되지 않는지도 확인.
- 공유 DB 데이터·스키마, 기존 미추적 파일, 브랜치, 커밋, 원격 저장소는 변경하지 않음.
