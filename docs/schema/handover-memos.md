# 인수인계 메모 테이블 추가안

상태: 팀 검토용 제안. 실제 DB에 적용하지 않았으며 자동 실행되지 않는다.
첨부된 `babi_DB_Real.sql`의 아기별 멤버 모델, 복합 외래키 및 소프트 삭제 방식을 따른다.
DDL은 같은 디렉터리의 `handover-memos.mysql.sql`이다.

## 컬럼

| 컬럼 | 의미 | 제약 |
| --- | --- | --- |
| id | 메모 ID | 자동 증가 기본키 |
| baby_id | 대상 아기 ID | 필수, babies.id 참조 |
| author_member_id | 작성자의 아기 멤버 ID | 필수, baby_members.id 참조 |
| content | 보호자가 직접 작성한 메모 | 필수, 최대 1000자 |
| created_at | 작성 시각 | 필수, DATETIME |

1000자 제한은 기존 메모 요청 DTO를 따른 제안이다. 작성자 없는 메모는 허용하지 않는다.
아기와 작성자 멤버의 조합을 복합 외래키로 검증한다. 작성자가 다른 아기의 멤버라면 INSERT가 실패한다.
메모는 아기에 연결하며 특정 브리핑에 종속시키지 않는다. 브리핑 재생성 후에도 원문 메모를 보존한다.
메모를 AI 요약에 포함하는 서비스 연동은 별도 작업이다.

## 기존 코드에서 바꿀 부분

- `groupId`는 제거한다. 현재 팀 모델에는 가족 그룹 테이블이 없다.
- 기존 `authorId` 사용자 ID 대신 `authorMemberId` 멤버 ID를 저장한다.
- 작성자는 요청 본문에서 받지 않고 인증된 사용자와 대상 아기로 멤버를 조회해 결정한다.
- 작성 전에 계정 활성 상태, 멤버의 `removed_at IS NULL`, 필요한 작성 권한을 검사한다.
- DB 외래키는 멤버의 활성 상태나 작성 권한까지 보장하지 않는다.
- 내용은 API에서도 `@NotBlank`, `@Size(max = 1000)`로 검증한다. SQL의 TRIM 검사는 일반 공백만 제거하므로 탭·줄바꿈 등의 공백 검증을 대신하지 않는다.
- 기존 메모 엔티티는 이 DDL과 바로 호환되지 않는다. 엔티티·서비스·테스트 수정 후 배포해야 한다.

## 적용 및 조회 기준

MySQL 8.0.16 이상, InnoDB 부모 테이블을 전제로 한다.
부모 테이블의 BIGINT 타입과 `baby_members(baby_id, id)` 고유키가 팀 원본 SQL과 일치해야 한다.
기존 테이블과 같은 엔진 및 문자셋을 사용하도록 기본 설정을 확인하고 적용한다.
SQL 파일에는 DROP, 기존 테이블 변경, 데이터 변경이 없다.
같은 이름의 테이블이 있으면 CREATE가 실패하도록 하여 기존 구조의 불일치를 숨기지 않는다.

팀 승인 후 담당자가 대상 스키마를 명확히 선택해서 추가 DDL만 실행한다.
첨부 원본 전체에는 DROP 구문이 있으므로 기존 데이터가 있는 DB에 원본 전체를 실행하면 안 된다.
현재 파일 작성은 운영 DB 변경이나 배포 승인을 의미하지 않는다.

작성 시각은 기존 메모 코드와 같은 Asia/Seoul 기준을 제안한다.
애플리케이션이 시각을 명시하고, DEFAULT CURRENT_TIMESTAMP를 사용할 때도 DB 세션 시간대를 맞춘다.
당일 조회는 `baby_id = ? AND created_at >= ? AND created_at < ?`로 필터링한다.
시작은 당일 00:00, 종료는 다음 날 00:00이며 `ORDER BY created_at, id`로 정렬한다.
같은 내용의 메모가 여러 번 작성될 수 있어 내용이나 날짜에 UNIQUE를 두지 않는다.
멤버를 내보내더라도 기존 메모는 보존한다. 하드 삭제는 외래키로 차단된다.

## 적용 전 검증 항목

- 정상 멤버의 메모 저장 성공 및 조회 순서 확인
- 다른 아기의 멤버를 작성자로 지정할 때 외래키 오류 확인
- 없는 아기·멤버 ID와 NULL 작성자 차단 확인
- 빈 문자열·일반 공백만 있는 내용 차단 확인
- API의 1000자 초과 및 공백 입력 차단 확인
- DB를 직접 연결한 검증과 실제 적용은 아직 수행하지 않음
